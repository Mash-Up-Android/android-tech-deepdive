### 1. 코루틴 & 코어

**Q. suspend 함수의 동작 원리**

* 컴파일러가 suspend 함수를 CPS 방식으로 변환해서 처리함
* 컴파일 시점에 함수 마지막에 Continuation 파라미터가 몰래 추가되는데 이게 나머지 실행을 담은 콜백 역할을 함
* 내부적으로 상태 머신이 돌면서 중단 지점마다 라벨을 부여함
* 실제 중단 시 스레드 점유를 풀어주고 비동기 작업이 끝나면 다음 라벨의 코드를 이어서 실행하는 구조임

**Q. launch vs async / Job vs SupervisorJob의 차이와 예외 전파 방식**

* **launch**: 결과를 기다리지 않고 에러가 나면 즉시 부모로 예외를 전파함
* **async**: 결과값이 필요할 때 쓰며 await를 부를 때 예외가 발생함
* **Job**: 자식 에러가 터지면 부모를 타고 올라가서 형제들까지 다 취소시키는 양방향 전파를 함
* **SupervisorJob**: 자식이 실패해도 부모나 형제에게 타격을 주지 않는 단방향 전파를 함. 독립적인 UI 작업이나 네트워크 통신을 묶어줄 때 필수적임

**Q. Scope, Context, Dispatchers 역할 차이**

* **Context**: 코루틴 실행 세팅값(Job, Dispatcher 등)을 모아둔 집합임
* **Scope**: Context를 감싸서 코루틴 생명주기를 관리하고 구조화된 동시성의 바운더리를 쳐줌
* **Dispatchers**: 작업 성격에 맞춰 스레드를 배정함. UI는 Main, 네트워크 처리는 IO, 무거운 연산은 Default 스레드풀을 씀

**Q. Flow 연산자 실전 사용 예시**

* **flowOn**: 백그라운드 처리를 보장하기 위해 업스트림 스레드를 바꿀 때 사용함
* **buffer**: 데이터 발행 속도가 소비 속도보다 빠를 때 병목을 막으려고 병렬로 처리함
* **conflate**: 중간값을 다 버리고 무조건 최신 값만 UI에 렌더링할 때 찰떡임
* **combine**: 검색어와 필터 옵션처럼 여러 Flow의 최신값을 엮어서 새로운 결과를 낼 때 씀
* **flatMapLatest**: 검색창 타이핑이 새로 들어올 때마다 이전 API 요청을 취소하고 최신 검색어만 요청할 때 핵심적으로 쓰임

**Q. 구조화된 동시성이 왜 중요한가요?**

* 부모가 죽을 때 자식 코루틴도 같이 깔끔하게 취소되도록 수명을 묶어두는 원칙임
* 전역 스코프를 막 써서 백그라운드에 메모리 누수가 생기는 걸 원천 차단해 줌
* 비동기 에러가 터졌을 때 예측이 가능하고 디버깅 흐름을 잡기 편해짐

### 2. 아키텍처

**Q. Clean Architecture 기반 레이어 분리와 멀티모듈 구조를 쓰는 이유**

* Presentation, Domain, Data 레이어로 관심사를 분리함
* 제일 안쪽의 순수 코틀린 모듈인 Domain이 바깥 프레임워크에 절대 의존하지 않도록 의존성을 역전시키는 것이 핵심임
* 멀티모듈로 쪼개면 잘못된 의존성 참조를 컴파일 단계에서 차단할 수 있음
* 피처별 병렬 개발이 쾌적해지고 빌드 캐시를 타서 빌드 속도도 개선됨

**Q. 단방향 데이터 흐름 어떻게 구현했나요?**

* 상태는 ViewModel에서 UI로만 흐르고 이벤트는 UI에서 ViewModel로만 전달되게 세팅함
* Compose 환경에서 ViewModel이 상태 변경 주도권을 꽉 잡고 단일 진실 공급원 역할을 함
* 사이드 이펙트를 줄이고 상태 추적이나 단위 테스트하기가 훨씬 수월해짐

**Q. UseCase 언제 쓰고, 언제 안 써도 되나요?**

* 여러 Repository를 엮거나 여러 ViewModel에서 비즈니스 로직을 재사용할 때 필수적임
* 하지만 데이터를 가공 없이 단순 전달만 하는 수준이라면 오히려 보일러플레이트가 될 수 있으므로 팀 컨벤션에 따라 유동적으로 생략하기도 함

### 3. 안드로이드 프레임워크

**Q. 환경 변화 시 데이터 유지 방법**

* 화면이 돌아가도 죽지 않는 ViewModel에 데이터를 두는 게 정석임
* 하지만 메모리 확보를 위해 OS가 프로세스 자체를 날려버리면 ViewModel도 죽음
* 이럴 땐 SavedStateHandle을 써서 복구용 핵심 ID 값 정도는 따로 저장해 두어야 함

**Q. 메모리 누수 단골 케이스 & 해결책**

* 싱글톤 같은 수명이 긴 객체가 Activity Context를 계속 붙잡고 있을 때 터지므로 Application Context로 우회해야 함
* 리스너를 등록해 놓고 라이프사이클에 맞춰서 해제하지 않았을 때도 흔하게 발생함
* 전역 스코프로 코루틴을 돌리다 액티비티를 캡처했을 때도 누수 원인이 됨
* LeakCanary를 띄워놓거나 메모리 프로파일러로 틈틈이 점검해서 잡음

**Q. ANR 발생 조건과 디버깅**

* 메인 스레드가 터치 이벤트를 5초 이상 처리하지 못하면 발생함
* 주로 메인 스레드에서 무거운 JSON 파싱이나 파일 입출력을 돌리거나 데드락에 빠졌을 때 터짐
* traces.txt 파일을 열어서 블로킹된 스레드를 확인하거나 플레이 콘솔 로그를 분석해서 백그라운드 스레드로 빼주는 작업을 함

**Q. RecyclerView 성능 최적화**

* 전체를 다 엎는 갱신 메서드는 지양하고 DiffUtil을 써서 바뀐 아이템만 부분 갱신함
* 크기 고정이면 옵션을 켜서 레이아웃 재계산 비용을 아끼고 이미지는 글라이드나 코일에 위임함
* 중첩 리스트 구조라면 뷰풀을 서로 공유하게 만들어서 스크롤 버벅임을 최적화함

**Q. Retrofit + OkHttp 토큰 갱신 구현**

* OkHttp의 Authenticator를 붙이는 게 제일 깔끔함
* 401 에러가 떨어지면 가로채서 토큰 갱신 API를 호출함
* 이때 API를 여러 번 호출하지 않도록 내부를 동기화 블록으로 묶어주는 게 가장 중요함
* 새 토큰을 받으면 실패했던 기존 요청의 헤더를 갈아끼워서 재요청을 쏨

**Q. WorkManager vs 포그라운드 서비스**

* **WorkManager**: 당장 안 해도 되지만 조건이 맞을 때 안정적으로 꼭 돌아가야 하는 로그 전송이나 동기화 작업에 씀. 앱이 꺼져도 보장됨
* **포그라운드 서비스**: 유저가 현재 진행 상황을 알림으로 꼭 인지해야 하는 음악 재생이나 파일 다운로드 같은 즉각적인 작업에 씀

**Q. 딥링크 vs 앱 링크**

* **커스텀 스킴 딥링크**: 똑같은 스킴을 쓰는 다른 앱이 있으면 선택 창이 떠서 유저 경험을 깎아먹음
* **앱 링크**: 웹사이트 도메인 소유권을 인증해 두면 다이얼로그 없이 바로 우리 앱으로 자연스럽게 연결해 줌

### 4. CS (Computer Science)

**Q. 프로세스 vs 스레드, 안드로이드 메인 스레드 역할**

* 프로세스는 OS한테 자원을 배정받은 독립 개체라 서로 메모리를 공유하지 않음
* 스레드는 그 안의 실행 흐름으로 스택만 따로 쓰고 힙 메모리는 같이 공유함
* 안드로이드 메인 스레드는 UI 그리기와 터치 이벤트를 전담하며 동시성 문제를 막기 위해 UI 업데이트는 오직 메인 스레드에서만 가능하게 강제해둠

**Q. 가비지 컬렉션 & ART 동작**

* 안드로이드 ART 런타임은 객체의 생존 기간에 따라 나누는 세대별 가비지 컬렉션을 사용함
* 생성된 지 얼마 안 된 수명이 짧은 객체 위주로 빠르게 메모리를 청소함
* 특히 앱 스레드와 병렬로 동작하는 방식을 채택해서 앱이 멈칫하는 현상을 최소화하고 UI 버벅임을 많이 잡아줌

**Q. HTTPS / JWT / OAuth 2.0 핵심**

* **HTTPS**: 처음 통신을 연결할 땐 안전한 비대칭 키로 세션키를 교환하고 그 뒤론 속도가 빠른 대칭 키로 실제 데이터를 주고받음
* **JWT**: 상태를 서버에 들고 있지 않는 토큰 방식임. 페이로드 자체는 단순 인코딩이라 민감 정보를 넣으면 안 됨
* **OAuth 2.0**: 유저 비밀번호를 직접 받지 않고 구글이나 카카오에 인증을 위임함. 모바일에선 인가 코드 탈취를 막기 위해 PKCE 적용이 필수임

**Q. HashMap equals / hashCode 계약**

* HashMap은 해시코드로 들어갈 버킷을 찾고 그 안에서 equals로 진짜 주인이 누군지 식별함
* 그래서 두 객체의 equals가 참이면 해시코드도 무조건 똑같아야 한다는 철칙이 있음
* 이걸 안 맞추면 똑같은 데이터를 넣어놓고도 나중에 못 찾는 대참사가 남. 해시 충돌이 심해지면 자바 8부턴 내부적으로 연결 리스트를 트리 구조로 바꿔서 탐색 속도를 방어해 줌
