# Configuration change 시 데이터 유지 방법

## 1. Configuration change 시에 무엇이 일어나는가
- Configuration change 예시
   - 화면 회전
   - 다크모드 전환
   - 폰트 사이즈 변경
   - etc
- Configuration이 바뀌면 Activity는 destroy 되고 다시 생성됨
- Configuration change 과정에서 Activity 멤버 변수는 모두 사라짐

## 2. 데이터 유지 방법

### ViewModel
- ViewModel은 Configuration change에서 살아남음 -> 시스템에 의해 프로세스가 죽으면 같이 사라짐
- 화면 단위 상태 관리에 가장 적합

### SavedInstanceState (Bundle)
- 프로세스가 시스템에 의해 종료된 후 복원될 때까지 살아남음
- 직렬화 가능한 작은 데이터만 가능

### SavedStateHandle (ViewModel + SavedInstanceState 결합)
- ViewModel 안에서도 프로세스 사망에 대비 가능

### Persistent Storage
- DB(Room), DataStore
- 앱 삭제 전까지 영구적으로 사용할 데이터

# 메모리 누수가 발생하는 대표적인 케이스와 해결 방법

## 1. 메모리 누수 정의
- GC가 회수해야 하는 객체가 다른 살아있는 객체에 참조되어 회수되지 못하는 상태
- 안드로이드에서는 보통 destroy된 Activity가 살아있는 객체에 잡혀 있는 경우가 가장 흔함

## 2. 대표 케이스

### 정적 참조에 Activity Context 저장
```kotlin
// 잘못
object SingletonManager {
    var context: Context? = null  // Activity Context 저장하면 누수
}
```

- 해결: Application Context 사용

### Inner class / 익명 클래스의 외부 참조
```kotlin
// 잘못 — Handler가 Activity를 암묵적으로 참조
class MyActivity : AppCompatActivity() {
    private val handler = Handler(Looper.getMainLooper())
    override fun onCreate(/* ... */) {
        handler.postDelayed({ /* ... */ }, 60_000)
        // Activity destroy 후에도 잠시동안 Activity 참조 유지됨
    }
}
```

- 해결: WeakReference 사용 또는 onDestroy에서 removeCallbacks

### 리스너/콜백 해제 누락
시스템에 등록한 것들은 반드시 명시적으로 해제해야 함

```kotlin
override fun onStart() {
    super.onStart()
    locationManager.requestLocationUpdates(/* ... */, locationListener)
}

override fun onStop() {
    locationManager.removeUpdates(locationListener)
    super.onStop()
}
```

### ViewBinding을 Fragment에서 잘못 다루는 경우
```kotlin
// 잘못: Fragment의 view는 onDestroyView에서 사라지지만 binding은 살아있음
private lateinit var binding: FragmentMyBinding

override fun onCreateView(/* ... */): View {
    _binding = FragmentMyBinding.inflate(inflater, container, false)
    return binding.root
}
```

- 해결: onDestroyView에서 binding 해제

### 스트림 구독 해제 누락
```kotlin
// 잘못
override fun onStart() {
    repository.observe()
        .collect { updateUI(it) } // Disposable 보관 안 함 → 누수
}
```

- 해결: 코루틴 - lifecycleScope/repeatOnLifecycle 사용

## 3. 검출 방법
- Android Studio Profiler - Heap dump 후 hprof 분석
- StrictMode - 메인 스레드 차단/리소스 누수 검출

# ANR이 발생하는 조건과 디버깅 방법, 실제 경험

## 1. ANR 트리거 조건

### ANR (Application Not Responding) 조건
- 입력 이벤트(터치/키)가 5초 이상 응답 없음
- BroadcastReceiver의 onReceive가 10초 이상 지연
- Service.onStartCommand가 20초 이상 지연
- ContentProvider의 onCreate() 실행이 10초 이상 지연

## 2. 발생 원인
1. 메인 스레드에서 무거운 작업 - 네트워크, DB I/O, 파일 I/O, 큰 비트맵 처리 등
2. 데드락 - 메인 스레드가 다른 스레드의 lock을 기다리는데 그 스레드가 메인을 기다리는 상황
3. 무한 루프 / 매우 깊은 재귀
4. 복잡한 레이아웃 인플레이션 - 중첩된 ViewGroup, 큰 ConstraintLayout
5. 시스템 부하 - system_server가 느려서 binder 호출이 지연

## 3. 디버깅 방법

### ApplicationExitInfo (Android 11+)
시스템이 직접 기록한 종료 사유를 저장

```kotlin
val am = getSystemService(ACTIVITY_SERVICE) as ActivityManager
val infos = am.getHistoricalProcessExitReasons(packageName, 0, 10)
infos.forEach {
    if (it.reason == ApplicationExitInfo.REASON_ANR) {
        val trace = it.traceInputStream?.bufferedReader()?.readText()
        Log.e("ANR", trace ?: "")
    }
}
```

### /data/anr/traces.txt 파일
- 버그 모드에서 dump 가능
- 각 ANR 발생 시 모든 스레드의 stack trace가 기록됨

### Firebase Crashlytics ANR 리포트
- Firebase Crashlytics를 이용한 방법 

# RecyclerView 성능 최적화

## 1. setHasFixedSize(true)
- RecyclerView 자체의 크기가 아이템 추가/삭제로 변하지 않는다는 것을 알려줌
- 변경 시 onMeasure를 다시 호출하지 않아 성능 향상에 도움

## 2. DiffUtil + ListAdapter
- notifyDataSetChanged()는 모든 ViewHolder를 다시 바인딩 -> 매우 비효율적
- DiffUtil은 두 리스트의 차이를 계산해 변경된 부분만 갱신

```kotlin
class MyAdapter : ListAdapter<Item, MyViewHolder>(DIFF_CALLBACK) {
    // submitList(newList) 만 호출하면 끝
    companion object {
        val DIFF_CALLBACK = object : DiffUtil.ItemCallback<Item>() {
            override fun areItemsTheSame(old: Item, new: Item) = old.id == new.id
            override fun areContentsTheSame(old: Item, new: Item) = old == new
        }
    }
}
```

## 3. ViewHolder 안에서 UI Event 새로 생성하지 않음
```kotlin
// 잘못
override fun onBindViewHolder(holder: VH, position: Int) {
    val item = items[position]
    holder.itemView.setOnClickListener { onItemClick(item) }
    // 매 바인딩마다 람다 새로 생성 → GC 압박
}

// 해결 - ViewHolder 생성 시점에 한 번만 등록
class ViewHolder(
    private val onClick: (Int) -> Unit,
    view: View,
) : RecyclerView.ViewHolder(view) {
    init {
        view.setOnClickListener {
            if (bindingAdapterPosition != RecyclerView.NO_POSITION) {
                onClick(bindingAdapterPosition)
            }
        }
    }
}
```

## 4. ViewHolder를 inner class로 만들지 말 것
- inner class는 외부 Adapter를 암묵적으로 참조 → 메모리 누수 유발
- nested class로 만들고 필요한 의존성은 생성자로 주입

## 5. setHasStableIds(true) + getItemId()
- 각 아이템에 고유 ID를 부여하면 RecyclerView가 더 정확하게 ViewHolder를 재사용
- DiffUtil와 별개로 성능 향상에 도움

## 6. nested RecyclerView - RecycledViewPool 공유
가로/세로로 RecyclerView가 중첩될 때 -> 자식 RecyclerView들이 풀을 공유하면 ViewHolder 재사용률이 상승

```kotlin
val sharedPool = RecyclerView.RecycledViewPool()
// 각 child RecyclerView에 set
childRecyclerView.setRecycledViewPool(sharedPool)
```

## 7. 레이아웃 평탄화
- ViewHolder 안의 레이아웃이 깊으면 inflate이 무거워짐
  - ConstraintLayout으로 평탄화
  - 가능하면 단일 <merge>

# Retrofit + OkHttp 환경에서 토근 갱신 구현

## 1. Authenticator
인증 실패에 반응하는 표준 메커니즘

- 호출 시점 - 401/407 응답 받았을 때
- 용도 - 토큰 갱신 (재요청용)
- 동기 (메소드 안에서 차단됨)

## 2. Interceptor
- 호출 시점 - 모든 요청/응답
- 용도 - 헤더 추가, 로깅, 재시도
- 동기

## 3. 어떤 것이 더 나은가
- Authenticator이 Interceptor보다 나음
  - Interceptor로 매번 만료 확인 후 갱신하는 방식보다 인증 실패에 반응하는 Authenticator이 깔끔

## 4. 주의 사항

### 1. refresh 요청 자체는 다른 OkHttpClient 사용
- refresh API 호출이 다시 토큰 만료 인터셉터를 타면 무한 루프 발생

### 2. 동시성 처리
- 여러 요청이 동시에 401을 받았을 때 refresh가 한 번만 실행되어야 함
- synchronized 블록 안에서 처리

### 3. refresh 실패 시 로그아웃 처리
- 토큰 정보 모두 삭제, 로그인 화면으로 이동 등 만료 로직 동작

# WorkManager, Foreground Service

## 1. WorkManager
- 지속적 - 앱이 종료되거나 기기가 재부팅되어도 보장 
- 제약 조건 지정 가능 -> 네트워크, 충전 중, 배터리 충분 등
- 정확한 시간이 아니라 적절한 시점에 실행
- 내부적으로 JobScheduler, AlarmManager, BroadcastReceiver를 API 레벨에 맞게 사용

### 신속 처리 작업 (Expedited Work)
- Android 12부터 추가된 setExpedited() API
- 시스템에 신속 처리 신호
- 12 이전 버전에서는 자동으로 Foreground Service로 fallback

## 2. Foreground Service
- 즉시 실행, 사용자가 인지함 - 알림 표시 필수
- 시스템이 종료할 가능성 매우 낮음
- Android 8+에서 백그라운드에서 직접 시작하려면 startForegroundService() 후 5초 안에 startForeground() 호출
- Android 12+ 백그라운드에서의 시작 제한 강화
- Android 14+ foreground service type 명시 필수

# 딥링크 / App Links 처리

## 1. 종류
- URI Scheme Deep Link - `myapp://detail/123` -> 임의 스킴으로 검증 없음
- Web Link Deep Link - `https://example.com/detail/123` -> autoVerify 없이 다른 앱과 충돌 시 chooser 표시
- Android App Links - `https://example.com/detail/123` + autoVerify=true -> 도메인 소유 검증 후 자동 라우팅

## 2. 인텐트 처리
```kotlin
class DetailActivity : AppCompatActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        handleIntent(intent)
    }

    override fun onNewIntent(intent: Intent) {
        super.onNewIntent(intent)
        handleIntent(intent)
    }

    private fun handleIntent(intent: Intent) {
        // 인텐트 처리
    }
}
```

- `launchMode="singleTask"` 또는 `"singleTop"` 을 매니페스트에 두면 새 액티비티 생성 대신 `onNewIntent`를 호출해 기존 인스턴스 재사용

## 3. Deferred Deep Link (지연 딥링크)
- 앱이 설치되어 있지 않을 때, 마켓 → 설치 → 첫 실행 시 원래 의도한 화면으로 이동시키는 패턴
- 드로이드/iOS는 직접 지원하지 않아 외부 솔루션 사용
