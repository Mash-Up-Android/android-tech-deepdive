# suspend 함수 동작 원리 (CPS 변환, Continuation)

## 1. 핵심 개념
suspend 키워드가 붙은 함수는 코틀린 컴파일러에 의해 CPS (Continuation Passing Style)로 변환됨

CPS란 함수가 다음에 실행할 코드를 명시적인 인자(Continuation)로 전달받아함수 내부에서 그 Continuation을 호출하는 방식

일반 함수는 Call Stack에 의존하여 호출자로 돌아가지만 코루틴은 스택이 비어 있어도 Continuation 객체에 어디서부터 다시 시작할지를 보존하기 때문에 non-blocking, 일시정지/재개가 가능

## 2. 컴파일러가 하는 일

```kotlin
suspend fun fetchUser(id: Int): User { 
    //...
}

// 컴파일러가 변환한 코드 (pseudo code)
fun fetchUser(id: Int, continuation: Continuation<User>): Any?
```

1. 마지막 파라미터로 Continuation<T>가 추가됨
2. 반환 타입이 Any?로 변경됨
   - 결과값(T) 또는 COROUTINE_SUSPENDED 마커를 반환해야 하기 때문
3. 함수 블록은 state machine으로 변환됨 - 각 suspension point마다 label 값을 부여하여 실행 상태 추적

## 3. 상태 머신 변환 예시

```kotlin
suspend fun loadUser(id: Int): User {
    val token = getToken() // 중단점 1
    val user = getUser(token, id) // 중단점 2
    return user
}
```

```kotlin
fun loadUser(id: Int, completion: Continuation<User>): Any? {
    class LoadUserStateMachine(
        // ...
    ) : ContinuationImpl(
        // ...
    ) {
        var label = 0
        var token: String? = null
        // ...
        override fun invokeSuspend(result: Result<Any?>): Any? {
            when (label) {
                0 -> { 
                    label = 1
                    return getToken(this)
                }
                
                1 -> { 
                    token = result.getOrThrow() as String
                    label = 2
                    return getUser(token, id, this)
                }
                
                2 -> { return result.getOrThrow() as User }
            }
        }
    }
    // 상태 머신 인스턴스 만들고 invokeSuspend 호출
}
```

## 4. Continuation 인터페이스

```kotlin
public interface Continuation<in T> {
    public val context: CoroutineContext
    public fun resumeWith(result: Result<T>)
}
```

- context - 이 Continuation이 속한 코루틴의 컨텍스트 (Job, Dispatcher 등)
- resumeWith() - 결과(성공/실패)와 함께 코루틴 실행을 재개

## 5. 왜 CPS를 쓰는가

스레드의 콜 스택을 유지한 채 일시정지하려면 그 스레드는 다른 작업을 못함
CPS로 변환하면 함수가 일시정지하는 순간 콜 스택이 비워지고 스레드는 즉시 다른 일을 할 수 있음
재개할 때는 보존해 둔 Continuation의 상태로부터 복구하기만 하면 됨

이것이 코루틴이 경량 스레드로 불리는 핵심 메커니즘

# launch vs async, Job vs SupervisorJob 차이와 예외 전파

## 1. launch vs async

| 구분    | launch | async |
|-------|---|--|
| 반환 타입 | Job | Deferred<T> |
| 결과 반환 | 없음 | await() 로 결과 받음 |
| 예외 처리 | 즉시 전파 | await() 호출 시점에 예외 throw |
| 사용 시기 | 결과가 필요 없는 작업 | 병렬 분해 + 결과 합치기 |

```kotlin
// launch: 결과가 필요없는 작업
viewModelScope.launch {
    repository.saveLog(event)
}

// async: 병렬 분해
viewModelScope.launch {
    val user = async { fetchUser() }
    val posts = async { fetchPosts() }
    showProfile(user.await(), posts.await()) // 두 작업 병렬 수행
}
```

- async로 시작한 코루틴이 루트 코루틴이 아니면 예외는 부모로 즉시 전파됨
- 루트일 때만 await() 시점까지 예외가 보존됨

## 2. Job 계층 구조와 예외 전파
코루틴은 부모-자식 관계로 트리 구조를 이룸

자식 코루틴에서 예외가 발생하면
1. 예외가 부모로 전파됨
2. 부모는 자기 자신과 모든 형제 코루틴을 취소
3. 다시 그 위 부모로 전파

이것이 일반적인 Job의 동작, 한 작업이 실패하면 전체가 실패

## 3. SupervisorJob의 차이
SupervisorJob은 자식의 예외를 부모로 전파시키지 않음
한 자식이 실패해도 다른 자식들은 계속 실행됨

```kotlin
val scope = CoroutineScope(SupervisorJob() + Dispatchers.Main)

scope.launch { task1() }  // 실패해도
scope.launch { task2() }  // 영향 없음
scope.launch { task3() }  // 영향 없음
```

- ViewModel의 viewModelScope은 내부적으로 SupervisorJob을 사용
    - 한 화면에서 여러 데이터를 동시에 요청할 때, 하나가 실패해도 나머지는 살아 있음

## 4. 자주 빠지는 함정
launch(SupervisorJob()) 형태로 빌더에 직접 SupervisorJob을 넘기는 것은 거의 잘못된 사용
빌더에 전달된 Job은 새 코루틴의 부모 Job이 되므로 코루틴 계층의 연결이 끊김 -> 구조화된 동시성이 깨짐

올바른 방법
1. CoroutineScope(SupervisorJob() + ...)로 스코프 자체를 만듦
2. supervisorScope { ... } 블록으로 일시적인 Supervisor 영역을 만듦

# CoroutineScope, CoroutineContext, Dispatchers 각각의 역할

## 1. CoroutineContext
코루틴이 어떻게 동작할지를 규정하는 indexed set

### 핵심요소
- Job - 코루틴의 생명주기 관리, 취소/완료 추적
- CoroutineDispatcher - 어떤 스레드에서 실행할지 결정
- CoroutineExceptionHandler - 처리되지 않은 예외 처리
- CoroutineName - 디버깅용 이름

`+` 연산자로 결합하며 같은 키의 요소를 더하면 뒤의 것이 앞의 것을 덮어씀

```kotlin
val context = Job() + Dispatchers.IO + CoroutineName("Loader")
```

## 2. CoroutineScope
CoroutineContext를 감싸는 컨테이너

launch, async 같은 빌더는 모두 CoroutineScope의 확장 함수

스코프가 취소되면 그 안의 모든 코루틴이 일괄 취소되기 때문에 생명주기에 묶인 작업을 관리하는 단위가 됨

```kotlin
class TempViewModel : ViewModel() {
    // viewModelScope: ViewModel이 cleared될 때 자동 취소
    fun load() {
        viewModelScope.launch {
            // ...
        }
    }
}
```

### 안드로이드에서 자주 쓰는 미리 정의된 스코프
- viewModelScope - ViewModel 생명주기, 내부적으로 SupervisorJob + Dispatchers.Main.immediate
- lifecycleScope - Activity/Fragment 생명주기
- GlobalScope - 앱 전체 생명주기 (사용 권장 안 함 - 누수 위험)

## 3. Dispatchers
스레드 풀을 추상화한 것으로 코루틴을 어떤 스레드에서 실행할지 결정

| Dispatcher | 용도 | 스레드 수 |
|---|---|---|
| Dispatchers.Main | UI 작업 (안드로이드 메인 스레드) | 1 |
| Dispatchers.Main.immediate | 이미 메인 스레드면 디스패치 없이 즉시 실행 | 1 |
| Dispatchers.IO | 네트워크, 디스크 I/O — 차단되는 작업 | 64+ (탄력적) |
| Dispatchers.Default | CPU 집약 작업 (정렬, 파싱 등) | CPU 코어 수 |
| Dispatchers.Unconfined | 호출 스레드에서 시작, 첫 중단 후 재개 스레드 따라감 | 보통 사용 X |

- withContext(Dispatcher) { ... }로 일시적으로 스위칭할 수 있음

# flowOn, buffer, conflate, combine, flatMapLatest 실전 사용 예시

## 1. flowOn - 업스트림 컨텍스트 변경
- 업스트림 연산(emit하는 쪽)을 어떤 디스패처에서 실행할지 지정함
- 다운스트림에는 영향이 없어 context preservation(컨텍스트 보존) 원칙을 위반하지 않고 안전하게 스레드를 바꿀 수 있음

## 2. buffer - 동시 실행으로 처리량 향상
```kotlin
flow {
    repeat(3) {
        delay(100)
        emit(it)
    }
}
.buffer()                  // 여기서 분리
.collect {
    delay(300)
    println(it)
}
```

- buffer() 없이는 emit과 collect가 직렬로 실행되어 총 (100 + 300) * 3 = 1200ms 가 걸림
- buffer()를 두면 producer가 대기 없이 계속 emit하므로 100 * 3 + 300 = 600ms 정도로 줄어듦

## 3. conflate - 중간 값 버리기
```kotlin
flow {
    repeat(10) {
        delay(50)
        emit(it)
    }
}.conflate()
.collect {
    delay(300)
    println("processed $it") // 0, 5, 9 같은 식 (중간값 스킵)
}
```

- 연속적으로 갱신되는 상태에 적합
- 모든 값을 다 받을 필요가 없을 때 씀

## 4. combine - 여러 Flow의 최신 값 결합
여러 Flow 중 하나라도 새 값을 emit하면, 각 Flow의 가장 최근 값을 조합해 결과를 만듦

- zip과 다름 - zip은 양쪽이 다 emit해야 짝을 이뤄 진행

## 5. flatMapLatest - 최신 입력에만 반응
업스트림에서 새 값이 오면 이전에 만든 내부 Flow를 취소하고 새 Flow로 전환

- 이전 결과가 늦게 도착해서 새 결과를 덮어쓰는 race condition을 자연스럽게 방지

# 구조화된 동시성(Structured Concurrency) 중요성

## 1. 핵심 원칙
코루틴은 항상 부모 스코프 안에서 시작되어야 하고, 부모는 모든 자식이 끝날 때까지 자신도 끝나지 않음

### 핵심 원리
1. 수명 보장 - 부모가 끝나면 모든 자식도 정리됨
2. 취소 전파 - 부모가 취소되면 자식도 자동 취소됨
3. 에러 전파 - 자식의 예외가 부모로 올라감

## 2. 왜 중요한가
GlobalScope.launch { ... }처럼 부모 없이 띄운 코루틴은 통제할 수 없음 
화면이 사라져도 계속 돌고, 누수가 되며, 결과가 어디서 오는지 추적이 어려움

## 3. coroutineScope vs supervisorScope
- coroutineScope {} - 하나의 자식이 실패하면 형제 모두 취소
- supervisorScope {} - 자식들이 독립적, 한 명 실패가 다른 형제에게 영향 없음

### 병렬 분해 (parallel decomposition)
- 둘 다 성공해야 의미 있는 작업에는 coroutineScope
- 각각 독립적으로 보여주면 되는 작업에는 supervisorScope
