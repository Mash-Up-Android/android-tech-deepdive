# Clean / APP Architecture 레이어 분리 (data/domain/presentation), 멀티모듈 구조

## 1. Clean Architecture vs App Architecture

### Clean Architecture
- 소프트웨어 공학 일반론. 특정 플랫폼에 종속되지 않은 범용 아키텍처 원칙
- 동심원 4개 레이어로 구성됨

레이어
- Entities - 엔터프라이즈 전반의 비즈니스 규칙
- Use Cases - 애플리케이션 고유의 비즈니스 규칙
- Interface Adapters - 데이터 형식 변환 (Controllers, Presenters, Gateways)
- Frameworks & Drivers - UI, DB, Web, 외부 인터페이스

### App Architecture (Google 공식 안드로이드 아키텍처)
구글이 공식 문서에서 권장하는 안드로이드 특화 아키텍처, 3-Layer 구조

레이어
- UI - Activity / Fragment / Compose + ViewModel + UI State
- Domain - UseCase (선택적, Optional)
- Data - Repository + Data Sources (Retrofit, Room 등)

특징
- Domain은 선택사항으로 명시되어 있음 (단순한 앱은 생략 가능)
- Clean Architecture의 Entity 개념은 채택하지 않음
- UI Layer 안에서 UDF(단방향 데이터 흐름) 패턴을 권장

## 2. 레이어 구조
안드로이드의 권장 아키텍처는 데이터의 흐름과 의존성 방향을 분리하기 위해 세 개의 레이어로 나눔

| 레이어 | 책임 | 의존성 |
|---|---|---|
| Presentation | UI, 상태 관리 (Activity/Fragment, ViewModel) | Domain |
| Domain | 비즈니스 로직 (UseCase, 모델, Repository 인터페이스) | 없음 (순수 Kotlin) |
| Data | 데이터 소스 통합 (Repository 구현, Retrofit, Room) | Domain |

## 3. 의존성 방향
의존성 역전 원칙(DIP)을 적용해, Data 레이어는 Domain의 인터페이스를 구현

- Domain은 안드로이드 SDK에 의존하지 않는 순수 Kotlin 모듈
- 이게 가능해야 비즈니스 로직을 다른 환경에 옮길 수도 있고, 무엇보다 테스트가 쉬워짐

## 4. 멀티모듈 구조
```
app/
├── presentation/   (Android 의존, domain 의존)
├── domain/         (순수 Kotlin)
└── data/           (Android 일부 의존, domain 의존)
```

```
app/
├── core/
│   ├── core-ui/          (공통 UI 컴포넌트)
│   ├── core-network/     (Retrofit 설정)
│   └── core-database/    (Room 설정)
├── feature/
│   ├── feature-home/
│   │   ├── presentation/
│   │   ├── domain/
│   │   └── data/
│   └── feature-profile/
│       ├── presentation/
│       ├── domain/
│       └── data/
└── app/                  (조립만)
```

### 장점
- 빌드 캐시 활용
- feature간 격리
- 점진적 컴파일

# 단방향 데이터 흐름(UDF)을 어떻게 구현했는지

## 1. 단방향 데이터 흐름 (UDF) 핵심 개념
UDF(Unidirectional Data Flow)는 상태는 한 방향으로만 흐른다는 원칙

- 상태(State)는 위에서 아래로 (ViewModel → UI)
- 이벤트(Event/Intent)는 아래에서 위로 (UI → ViewModel)

UI는 상태를 읽기만 하고 상태를 변경하고 싶을 때는 ViewModel에 이벤트를 전달

## 2. 왜 UDF인가
- 예측 가능 - 상태가 어디서 바뀌는지 한 곳에서만 봄
- 테스트 용이성 - ViewModel만 테스트하면 비즈니스 로직 검증 완료
- Configuration Change 안전 - ViewModel은 회전을 견디므로 상태가 유지됨
- Compose 친화적 - Compose는 상태가 변하면 자동으로 다시 그림 -> UDF와 궁합이 좋음

# UseCase가 왜 필요한지, 없어도 되는 경우는 언제인지

## 1. UseCase
UseCase는 사용자가 시스템에 대해 수행할 수 있는 하나의 행동을 나타내는 클래스

```kotlin
class GetUserProfileUseCase(
    private val userRepository: UserRepository,
    private val settingsRepository: SettingsRepository
) {
    suspend operator fun invoke(userId: String): UserProfile {
        val user = userRepository.getUser(userId)
        val settings = settingsRepository.getSettings(userId)
        return UserProfile(user, settings)
    }
}
```

## 2. 왜 필요한가
- ViewModel이 가벼워짐
  - UseCase 없이 ViewModel이 여러 Repository를 직접 다루면 비즈니스 로직까지 떠안는 God Object
- 비즈니스 로직 재사용
  - 같은 행동이 여러 화면에서 발생한다면 UseCase로 빼두면 여러 ViewModel들이 같은 UseCase를 주입받아 쓸 수 있음
- 테스트가 명확해짐
  - UseCase 단위로 테스트를 작성하면 비즈니스 규칙을 ViewModel과 분리해서 검증할 수 있음

## 3. 없어도 되는 경우
UseCase가 단순히 Repository 메서드를 그대로 호출하기만 하는 thin wrapper라면 강제로 만드는 게 의미 없을 수 있음

```kotlin
// 이건 굳이 필요할까?
class GetUserUseCase(private val repo: UserRepository) {
    suspend operator fun invoke(id: String) = repo.getUser(id)
}
```

일관성 관점을 중시한다면 여전히 둘 수 있음
